# EB521 V1.2 云台与 UART

R2 默认 AP 配置启用 `CONFIG_MYBOT_GIMBAL`，通过 UART2 连接 V1.2 协议的 EB521 底板。
首次使用时，上板自动请求充电并开始回中。之后上电会恢复用户保存的选择。语音和串口调试通过同一个 UART 任务提交绝对角度。底板可以稍后接入。

## 接线与串口

| 信号 | BK7259 | EB521 |
| --- | --- | --- |
| TX | GPIO2 / UART2_TX | RX |
| RX | GPIO3 / UART2_RX | TX |
| GND | GND | GND |

UART 参数为 115200、8 数据位、无校验、1 停止位、无流控。GPIO3 使用内部上拉保持空闲高电平。
UART worker 从 `0x61` 运动帧切到 `0x66` 供电或探测帧，以及反向切换时，均保留至少 40 ms 的估算线上空闲时间。
供电帧发送后，若下一步动作已到期，worker 等到这 40 ms 结束，再按轨迹当前时间下发目标。期间继续接收应答。供电状态稳定时，上板从上一条供电帧提交返回起至少等待 2000 ms，再发下一条。
联调时可在 CN1 的 2 脚观察请求、3 脚观察应答，均以 4 脚 GND 为参考。

## 协议

帧格式：

```text
03 + command + BE16(payload_length) + payload + LE16(Modbus-CRC16)
```

CRC 初值为 `FFFF`，多项式为 `A001`，覆盖帧头到 payload 末尾。单帧总长不超过
200 字节。

- `0x61` 下发左右、上下两轴绝对角度。角度以 0.1° 为单位，向右和向下为正。
  日常动作的限位为左右 ±80°、上仰 20°、下俯 10°。极限自检的目标范围为左右 ±90°、上仰 30°、下俯 15°。速度字段范围为 1～1000 pps，
  底板按 `floor(5000 / pps)` 毫秒每度执行。上板按每轴相邻目标的角度差和采样间隔
  选择能按时到达的最低 PPS。例如 3° 走 100 ms，使用 148 pps，协议预计耗时 99 ms。
- `E1/00` 表示开始转动，后续 `E1/06` 回显目标坐标。`E1/04` 表示已经到位。
  `E1/01` 表示开机演示未结束，`E1/02` 表示速度非法。底板对新接收的有效绝对目标立即执行覆盖。
- `0x66/01` 请求或续期充电。V1.2 协议给出的周期为 1000 ms，本测试固件使用 2000 ms。`0x66/00` 停止充电。`E6/00`
  表示底板已执行请求，`E6/02` 表示控制字节非法。有效续期间隔达到 3000 ms 时，
  底板关闭充电。

## 上电、热插拔与回中

启用舵机控制时，上电后发送双轴绝对目标 `(0,0)`，两轴速度均为 1000 pps。每秒再尝试一次，直到收到
可归属于回中的 `E1/04`，或坐标为 `(0,0)` 的 `E1/06`。`E1/00` 只确认开始，
充电心跳的 `E6` 只确认充电请求。回中期间丢弃普通动作，底板缺席时语音和屏幕可以正常启动。
舵机控制保存为关闭后，下次开机不发送运动帧。

已确认中位后，按轨迹发送最新的绝对目标。采用分段缓动的轨迹从获得发送时隙时估计的双轴角度衔接，大角度移动会延长过渡。思考和聆听直接下发各段的终点。
普通运动相邻两次 UART 提交尝试至少相隔 100 ms。成功提交一条普通 `0x61` 后，
`E1/00` 记录云台已接令。两轴坐标与本条目标一致的 `E1/06`，或可明确归属本条命令的
`E1/04`，确认本步到位。到位后按轨迹和 UART 发送间隔执行下一步。
从 UART 写入成功返回起计时。普通分解动作按两轴中较长的预计行程耗时加 100 ms 通信余量等待，
下限为 250 ms，上限为 2000 ms。回中每次等待 900 ms。
到期后将本步计为到位超时，直接推进。新对话阶段可接管旧动作，归属不清的迟到应答不能确认新目标。
等待期间照常接收 UART 和调度供电。挂断后按上文的回中流程执行。
每个计划采样点只尝试提交一条普通 `0x61` 帧。UART 提交失败也会消费这个采样点。
下一时隙按上一条成功提交的目标和速度，以及已经过去的时间，估算两轴当前位置，并为新的绝对目标重算 PPS。
如果需要超过速度上限才能到达，就延长本段。最后一个普通目标提交失败时仅计入 `tx_failed`，
该目标没有完成确认，也不会单独重发。独立回中继续等待确认。
开心摆动有幅度渐入和渐出。愤怒依次转到 +8°（300 ms）、−8°（500 ms），再用 410 ms 回到中位。
惊讶用 800 ms 转到 +30°，停留 300 ms，再用 650 ms 回到中位。
挂断会清除未发送的动作，并以同样的速度和周期回中直到确认。底板返回开机演示，或连续约 3.25 秒收不到有效运动或充电应答时，
上板清除旧位置和旧动作，再次确认中位。重新就绪后按当前阶段执行。
协议没有独立的拔插通知，极短的断开可能落在两次通信之间。

## 设置菜单

两个选项独立保存，按钮文字显示下一次点击会执行的操作。

- **关闭舵机控制**会丢弃待发动作，发送一条 `0x61` 双轴绝对回中指令，目标为 `(0,0)`，两轴速度均为 1000 pps。无应答时也只发送一次。再次点击**开启舵机控制**后，上板先确认回中，然后跟随当前对话阶段。
- **关闭供电请求**会主动发送 `0x66/00` 停充，随后每 2 秒维持停充。再次点击**开启供电请求**会主动发送 `0x66/01`，随后每 2 秒续期。
- 菜单显示上板的供电许可。实际充电电流可通过底板指示或电流表核验。恢复出厂后两项均开启。

设置变更先在本次运行生效，再写入 EasyFlash。菜单显示“保存失败，点击重试”时，轻触提示可重新保存。上电读取到无效记录时，两项都关闭。EasyFlash 将缺失的记录报告为首次使用；若底层已丢弃损坏的记录，也会使用首次启动的默认值。

## CLI

在设备待机、舵机控制已开启并出现 `gimbal center confirmed` 后开始测试。每次只输入一行命令，省略串口提示符 `$`。运动命令返回 `gimbal motion queued` 表示请求已受理。

| 测试项目 | 串口命令 | 操作和观察 |
|---|---|---|
| 全部动作 | `ap_cmd gimbal_test` | 受理后倒计时 10 秒，设备继续供电时可拔 Type-C。依次测试六个对话阶段和四个表情场景，结束后用 `gimbal_stats` 读取本轮报表。 |
| 极限角度与划 X | `ap_cmd gimbal_limit_test` | 10 秒后测试上下左右端点，再沿两条满跨度对角线正反各走一遍。结束后用 `gimbal_stats` 查看 17 步的结果。 |
| 查询统计 | `ap_cmd gimbal_stats` | 查看普通动作、回中、供电的应答成功率和耗时。自检完成或中断后读取冻结结果。 |
| 清零统计 | `ap_cmd gimbal_stats reset` | 单测前执行。自检在正式开始时自动清零，倒计时和运行期间手动清零会返回 `busy`。 |
| 开场 | `ap_cmd gimbal_dialogue start` | 从空闲进入模拟对话。云台从中位向右轻转 3.5° 后回正，全程约 0.5 秒。 |
| 聆听 | `ap_cmd gimbal_dialogue listening` | 从中位保持约 5 秒，观察第 3.5 秒左右开始的第一次点头。低头 3°、回正各发一条普通动作指令。 |
| 思考、处理中 | `ap_cmd gimbal_dialogue thinking` | 从中位用一条指令向右转 12°。观察转动途中是否连贯，继续保持此阶段可确认云台在右侧停住。 |
| 回答 | `ap_cmd gimbal_dialogue speaking` | 在设备静音时也可测试。观察云台水平左右各摆约 6°，每 1.25 秒往返一次，直到切换阶段或挂断。 |
| 中性 | `ap_cmd gimbal_dialogue neutral` | 模拟对话中切到中性，云台平滑回正。空闲时直接进入中性阶段也会触发开场。 |
| 挂断回中 | `ap_cmd gimbal_dialogue end` | 结束云台侧模拟对话，并等待日志 `gimbal center confirmed`。 |
| 开心 | `ap_cmd gimbal_scene happy` | 左右轻摆约 ±6°，结束后回中。 |
| 悲伤 | `ap_cmd gimbal_scene sad` | 约 3 秒缓慢低头至 10°，随后回正。 |
| 愤怒 | `ap_cmd gimbal_scene angry` | 水平轴先向右转 8°，再向左转到 −8°，随后回中。 |
| 惊讶 | `ap_cmd gimbal_scene surprised` | 向右转 30°，短暂停留后回中。 |
| 轮换表情 | `ap_cmd gimbal_scene` | 每次受理播放一个场景，顺序为开心、悲伤、愤怒、惊讶，随后循环。 |
| 方向校验 | `ap_cmd gimbal_cmd` | 每次受理切换到下一个绝对目标，依次为左 30°、下 10°、上 20°、右 10°。每次等到位再发下一条，测完用 `gimbal_dialogue end` 回中。 |
| UART 链路探测 | `ap_cmd gimbal_probe` | 可选。查看日志 `UART probe E6/02 verified` 确认底板回应。 |
| 开启供电请求 | `ap_cmd gimbal_charge on` | 开启底板给上板充电的请求，稳定时每 2 秒续期。此选择会保存到下次启动。 |
| 关闭供电请求 | `ap_cmd gimbal_charge off` | 请求底板停止给上板充电，稳定时每 2 秒维持停充。此选择会保存到下次启动。 |

对话阶段命令只驱动云台。测单个动作时，先清零，执行选定动作，结束后等约 1 秒再查统计。
四个表情场景会自动回中。模拟对话会保持当前阶段，手动发送 `ap_cmd gimbal_dialogue end` 并等回中确认后再查报表，这轮总数包含挂断回中。

`normal` 统计普通动作，`home` 统计回中。短应答匹配窗口分别为 250 ms 和 900 ms。
`tx` 是送入 UART 的帧数，`tx_failed` 是提交失败数。成功率为
`accepted / (accepted + rejected + timeout + overflow)`。仍在等待应答的 `pending` 和
提交失败的 `tx_failed` 单独显示。统计队列溢出导致无法跟踪的请求保留在分母中。
`accepted` 包含底板报告开始或已到位的请求，`completion_fallback` 是通过匹配到位帧补记的接受数。

`arrival normal` 和 `arrival home` 显示各自的到位结果。`reached` 为确认到位数，
`timeout` 为等到期仍未确认的次数，`cancelled` 为旧动作被接管等原因导致等待取消的次数。
到位率为 `reached / (reached + timeout + rejected + overflow)`。尚在等待和主动取消的帧单独列出。
自检报表的 `arrival speaking` 等行可用于逐阶段比较。

汇总行中的 `motion tx` 包含普通动作和回中。`short_ok_rx` 统计收到的全部有效 `E1/00`、`E1/04`
短应答，`short_ok_matched` 统计已归属到命令并计入成功的短应答。两者的差值可用来查看反馈归属的影响。
`center_confirmed` 统计控制程序在本轮记录的回中到位事件，每出现一次 `gimbal center confirmed` 就加一。
`tx_guard` 显示固定的 40 ms 发送保护间隔，`ordinary_period` 显示普通动作的 100 ms 提交周期。
`move_to_charge` 和 `charge_to_move` 分别显示
`0x61` 与 `0x66` 两个交替方向的样本数 `pairs` 和最短线上空闲估算 `min_idle_est`。
固件从前一次 UART 写入返回时刻到本次写入时刻的差值中扣除前一帧保守估算的剩余发送时长。
无样本时显示 `n/a`。

`power 00` 记录停充，`power 01` 记录启充或续期。`power` 合计两类请求，以
`accepted / (accepted + rejected + timeout)` 计算成功率。等待中的请求和 UART 提交失败单独列出。
`power_latency` 显示从成功提交到上板处理可匹配 E6 应答的样本数和最短、平均、中位、最长耗时。供电应答窗口为
250 ms。供电计数和延迟采样只涵盖 `0x66/00` 与 `0x66/01`，`0x66/02` 探测另行处理。
`power E6` 行的 `matched_00` 和 `matched_02` 分别统计已归属到供电请求的成功与拒绝应答。
同一行还列出无效应答 `bad`、迟到应答 `late`、未匹配应答 `unmatched` 和过滤的清零前应答 `suppressed`。

输出还显示原始 E1 结果码、无效应答 `bad`、未匹配应答 `unmatched`、归属不明的应答
`ambiguous`，以及过滤掉的重置前应答 `suppressed`。短应答不带事务编号，
前一帧超时后的迟到应答可能与新帧回包混淆，归属含估算的结果计入 `estimated`。
`latency` 从上板成功提交 UART 帧算到上板处理可单独匹配的首个短应答。
`arrival_latency` 从同一发送时刻算到上板处理可归属的到位确认，包含已在目标位置时的 `E1/04`。
两项耗时都包含接收轮询和任务调度时间。
其中 `n` 是本轮采样数，`min`、`max`、`avg` 和 `median` 分别为最短、最长、平均和中位耗时（ms）。
中位数覆盖自启动或上次清零以来的全部有效样本，样本数为偶数时取中间两项的均值。
若单独验证回中，可在待机且已确认中位后静置 1 秒，依次执行 `ap_cmd gimbal_stats reset`、
`ap_cmd gimbal_dialogue end`。等约 2 秒后查统计，并对照驱动的 `gimbal center confirmed` 日志。

## 对话联动

| 事件 | 屏幕与云台表现 |
| --- | --- |
| 会话建立 | 屏幕短暂显示惊讶。会话以中性阶段建立且云台已确认中位时，用约 250 ms 向右轻转 3.5°，再用约 250 ms 回正。会话建立时已有有效的非中性阶段，则直接执行该阶段。 |
| 聆听 | 显示聆听表情。连续聆听满 3.5 秒后，用一条绝对角度指令低头 3°，再用一条回正。从中位起步时俯仰速度为 27 PPS，单程预计 555 ms。持续聆听时，每隔约 3.5 秒点一次头。 |
| 思考 | 显示思考表情。从中位用一条绝对角度指令向右转 12°，水平速度为 85 PPS，预计行程 696 ms。云台随后保持该姿势直到阶段切换。思考持续 3 秒后，屏幕转为处理中。 |
| 回答 | 显示微笑的中性表情。云台水平目标按 ±6° 的正弦轨迹摆动，周期 1.25 秒，俯仰目标为 0°。句间停顿时，只要仍处于回答阶段就继续摆动。 |
| 挂断、断网或进入配网 | 取消待执行的对话动作并回中，收到中位确认后重新开放控制。 |

聆听、思考和回答以 SDK 上报的阶段为准。阶段切换会接管剩余开场动作和上一阶段的动作。相同阶段的重复通知保留原有计时。

## 一键云台测试

开启舵机控制，等串口出现 `gimbal center confirmed`。退出实际对话并让云台空闲，再执行 `ap_cmd gimbal_test`。
收到 `gimbal_test scheduled in 10s. You can unplug Type-C now.` 后，确保设备仍由电池或其他电源供电，再拔下
Type-C。测试由固件任务在 10 秒后开始。

测试依次执行开场（至少 0.9 秒，且等待动作走完）、聆听（5 秒）、思考（6 秒）、回答（4 秒）、中性（1 秒）和挂断回中，再依次
执行开心、难过、愤怒和惊讶场景。回答阶段的 4 秒使用实际对话的固定摆头动作。挂断及每个表情场景结束时，测试会等待回中确认。
实际对话开始、外部对话阶段更新、显式请求回中、关闭舵机控制或关闭设备会中断测试。测试期间
`gimbal_cmd` 和 `gimbal_scene` 返回 `busy`。底板断开或回中一直没有确认时，报表保留中断时的阶段和计数。

重新插入 Type-C 后执行 `ap_cmd gimbal_stats`。输出首行显示 `test` 状态和 `stage` 阶段。状态为
`scheduled` 时正在倒计时，为 `running` 时可查看本轮进度，为 `completed` 或 `interrupted` 时可读取冻结的一轮。
中断时 `stage` 显示最后执行的阶段，倒计时期间中断显示 `none`。
每个阶段单独列出发送、接受、拒绝、超时、溢出和提交失败数。原有汇总、反馈及延迟行也对应这一轮。
每个阶段还以 `motion_pairs` 和 `min_motion_gap` 显示普通 `0x61` 帧间隔的样本数及最小值（ms）。
同一阶段内，按相邻两条普通运动帧成功提交 UART 返回时的毫秒计时差取样。两帧之间可有 `0x66`，回中帧不计。
无样本时，最小值显示 `n/a`。
下一轮测试或成功清零后替换保存的结果。

## 极限角度与划 X 自检

云台待机、已确认回中时，执行 `ap_cmd gimbal_limit_test`。收到倒计时提示后，有 10 秒可以拔掉 Type-C 线。
设备由电池或其他电源继续供电。测试从中位出发，每段只发送一条 `0x61`。

| 步骤 | 路线（角度按水平、俯仰排列） |
|---|---|
| 1～4 | 上 `(0°, −30°)` → 中位 → 下 `(0°, +15°)` → 中位 |
| 5～8 | 左 `(−90°, 0°)` → 中位 → 右 `(+90°, 0°)` → 中位 |
| 9～10 | 到左上 `(−90°, −30°)`，第一笔从左上划到右下 `(+90°, +15°)` |
| 11～12 | 沿右边到右上 `(+90°, −30°)`，第二笔从右上划到左下 `(−90°, +15°)` |
| 13～14 | 沿下边到右下，第三笔从右下划到左上 |
| 15～16 | 沿左边到左下，第四笔从左下划到右上 |
| 17 | 从右上回中位 `(0°, 0°)` |

第 10、12、14、16 步各画一笔。水平以 1000 PPS 走 180°，俯仰以 250 PPS 走 45°，两轴预计同时在 900 ms 后到位。
每笔从一个角点直接走到对角，到位等待上限为 1000 ms。按两轴角度计算，X 的交点在水平 0°、上仰 7.5°。
其余步骤两轴速度均设为 1000 PPS。每步收到可归属的 `E1/06` 或 `E1/04` 后，在发送下一步前停留 500 ms。
一轮正常完成共 17 条运动指令，供电心跳单独统计。

重新连接 Type-C，执行 `ap_cmd gimbal_stats`。完整走完时首行显示 `test=completed mode=limit`，
每步应为 `tx=1 result=reached`。用 `ack_ms` 和 `arrival_ms` 分别核对短应答及到位耗时，
四笔斜线对应的记录应显示 `pan_pps=1000 pitch_pps=250`。
本步写入失败、被拒绝或等待到位超时时，程序中断自检、保留结果并请求回中。对照固定机位录像或角度刻度，
可将实际机械行程与底板报告的到位结果逐步核对。

在云台已确认中位、尚未进入真实对话时，可用串口验证开场抢占。

1. 先执行 `ap_cmd gimbal_dialogue start`，等开场走完，再执行 `ap_cmd gimbal_dialogue end` 并等待 `gimbal center confirmed`。这一轮作为完整开场的参照。
2. 将 `ap_cmd gimbal_dialogue start` 和 `ap_cmd gimbal_dialogue thinking` 连续发送。若思考指令在开场期间到达，云台应从当时位置转入思考，取消剩余开场目标。重复发送 `thinking` 应保留思考计时。结束后执行 `ap_cmd gimbal_dialogue end`。
3. 实际开聊一次，并观察屏幕阶段与云台动作。若真实阶段在开场期间切换，云台应衔接新阶段。实板一键自检保留完整开场和后续各阶段，可用 `ap_cmd gimbal_test` 复测整条轨迹。
