# EB521 云台四种 MCP 动作接入方案

日期：2026-10-13。本文方案的历史来源分支为 `release/v4.0.1-mybot-r2`。
当前官方工程为 `agora-r2-standard-devkit`，使用 `main` 分支。
本文保留当时的云台接入方案与测试方法。2026-10-16的实际配置以
[工程说明](../projects/mybot/README_CN.md)为准：舵机控制默认关闭，
重新启用后提供手动CLI；MCP表情仅渲染LCD，不驱动云台。音频已改用三路模拟输入及
追加数字参考，VAD关闭。下文的自动动作接入及ADC2回采描述属于历史方案。

已确认：两轴均为 0.315°/拍，允许 1000 pps，动作精度约 90% 即可；每条运动命令
确认完成后再下发下一条；新动作在当前小段结束后替换未下发轨迹；每个动作结束及
挂断均回到 (0,0)。`0x64` 不清除未完成任务，不能用于动作抢占或清队列。
最新物理行程为左右各 80°、向上 20°、向下 10°，替代此前的 180°/60°描述。

## 范围与现有接口

接入 `emotion.happy`、`emotion.sad`、`emotion.angry`、`emotion.surprised` 四个 MCP 场景。
当时 SDK 基线为 `7a10696ff27dd947da0558104da6c5414929ea09`。SDK 已解析 RTM
DeviceCommand v1，并通过 `mybot_lcd_content_t.indicators` 的 HAPPY/SAD/ANGRY/SURPRISED
位发出一次性表情请求。平台使用公开 `mybot/platform/mybot_lcd.h`，不重新解析 RTM，
不读取 SDK 私有状态，不新增 SDK 或 Agora 接口。

```mermaid
flowchart LR
    A[服务器 MCP 场景] --> B[RTM DeviceCommand]
    B --> C[agent-studio-device-firmware SDK 会话校验与去重]
    C --> D[LCD render 一次性表情位]
    D --> E[BK7259 场景请求]
    E --> F[原 UI owner：对应表情]
    E --> G[云台 owner：轨迹与 UART]
    G --> H[EB521 双轴步进云台]
```

SDK 命令格式和最近 16 个 command ID 的会话内 FIFO 去重沿用现状，时间字段仍为可选且忽略。
GPIO47 按键、音量、ADC2 回采 AEC、视频、状态/VP 第三行不引入新的控制路径。

## UART 与接线

参考 R2 的 `components/bk_servo/bk_hiwonder_car.c` 使用 UART5、GPIO65/64、1 Mbps，
采用 AA55/CRC8 协议。GPIO65/64 当前用于摄像头 I²C，不能复用该串口或协议。
生产接线按厂家提供的 `mcp-resource/usr_gpio_cfg.diff` 选择 UART2、GPIO2/3，
对应原理图中的 CN1 POGO 串口线：

| 信号 | BK7259 | CN1 | EB521 |
| --- | --- | --- | --- |
| 发送 | GPIO2 / UART2_TX | 2 | RX |
| 接收 | GPIO3 / UART2_RX | 3 | TX |
| 共地 | GND | 4 | GND |

方案采用 AP `UART_ID_2`，115200、8 数据位、无校验、1 停止位、无流控、DMA 关闭。
EB521 的 UART 电平及电机供电需按实际连接确认，不根据串口连接器推定电机供电。
资料没有给出 BK7259 控制 EB521 电源的使能脚，方案不借用其它电机模块的电源 GPIO。

当前 AVDK 的 UART 驱动支持 UART2 寄存器、时钟、IRQ 与自动引脚映射。
AP `usr_gpio_cfg.h` 配置 GPIO2/3 的 UART2 TXD/RXD 表项，平台初始化及
恢复时显式调用按功能映射的 GPIO API。UART2 功能选择分别为 TXD=100、RXD=99，
使用公开枚举，避免手写寄存器。不修改 AVDK。

## 协议实现

帧格式为 `03 + command + BE16(payload_length) + payload + LE16(CRC)`，总长不超过
200 字节。CRC 为 Modbus CRC16，初值 FFFF、多项式 A001，覆盖帧头到数据末尾。
角度为有符号小端 int16，单位 0.1°；速度为小端 uint16，单位 pps。
所有运动请求显式填写 1～1000 的有效速度；使用各命令条款的约束，不发送速度 0。

使用以下命令：

- `0x61`：两轴绝对角度，用于轨迹目标，避免相对角度累积误差。
- `0x63`：查询归零流程、实际角度、速度和运动标志。
- `0x64`：协议保留的停止命令；不用于正常动作切换、挂断或清队列。
- `0x65`：协议保留的重新归零命令；首版依赖上电自动归零，不在每次会话或动作时发送。

上电先查询自动归零结果；流程字节 02 才允许发送角度请求。复位 ACK 只表示接受，
不表示归零完成。归零等待有有限超时，失败时标记不可执行，不循环触发大幅度复位。
PDF 的控制器内置寻零流程包含先向左 180°、向上 60°；这与最新应用物理行程不同，
实物验收需核对控制器的寻零行为。BK 端运行限幅无法改变控制器自身的上电寻零流程，
首版不主动发送 `0x65`。

串行规则已确定：发一条 `0x61`，收到表示执行完成的应答后，才能发下一条 `0x61`。
设备端始终只保持一个未完成的运动请求，不使用控制器的三条任务队列。

应答命令字等于请求命令字加 `0x80`，例如 `0x61` 对应 `0xE1`。用户提供的实测
`03 E1 00 01 00 57 AC` 帧长度和 CRC 正确，按 PDF 定义表示接受，不代表完成。
E1/长度5/结果06 才是完成通知。第一条实测请求为绝对 −30°、500 pps；若从中心
出发约需 190 ms，而接受应答在 63 ms 返回。实测没有记录起点或后续完成帧，
不能仅根据接受帧推断已经到位。

正常等待当前接受应答之后的 06 完成帧，校验其中实际角度符合当前目标，并用新状态
查询核实停止且到位，避免迟到的旧完成帧推进新动作。若控制器只返回 00，
则通过串行 `0x63` 查询确认：E3/长度12、结果00、归零流程02、两轴标志 bit0
均为0，且两轴实际角度均在目标容差内，才允许发送下一个运动目标。
新运动及查询事务前丢弃已缓存、已到达的旧应答；查询命令也只保留一个在途请求，
每次查询收到应答后才能发下一次查询。协议没有序号，无法严格区分新事务发出后才到达的
任意重复旧帧；通过单运动在途、目标校验、状态核对，以及运动超时后禁用调度降低影响。
不以速度字段为0判停，不以等待预计运动时间代替完成确认。
04 表示已到目标，无需等待不存在的完成帧。01、02、03、05 分别按归零中、非法参数、
量化后零步、队列满处理；03 跳过没有实际位移的点，05 视为违反单任务约定的异常。

接收解析覆盖半帧、粘包、噪声、非法长度和 CRC 错误，使用固定缓冲和逐帧校验。
运动完成应答、查询应答与其它应答分别解析。正常切换先确认当前段完成，再启动
新动作；以查询确认完成时，迟到的 00 接受帧不推进轨迹，06 完成帧必须匹配当前目标。
协议没有命令序号，超时后不直接开启新轨迹，避免旧动作迟到应答推进新动作。
不盲目重发可能已经接受的角度请求；进入故障状态、停止继续下发并记录错误。
若故障时有可能尚未完成的运动，worker 仅尝试一次 `0x64` 双轴保持停止，并查询停止状态。
该命令仍顺序执行，不清队列；停止无法确认时明确记录，不宣称已经停止，不触发重新寻零。

## 角度、速度与行程

两轴按已确认的 0.315°/拍进行时间换算：

```text
所需拍数 ≈ abs(目标角度 − 当前角度) / 0.315
运动时间 ≈ 拍数 × 换拍间隔
```

协议按整数毫秒计算换拍间隔，`interval_ms = floor(1000 / pps)`。
实际速度是 `1000 / interval_ms`，因此不要用任意 pps 数值假设连续可调的角速度。

| 下发速度 | 换拍间隔 | 实际角速度 |
| --- | --- | --- |
| 20 pps | 50 ms | 6.3°/秒 |
| 100 pps | 10 ms | 31.5°/秒 |
| 200 pps | 5 ms | 63°/秒 |
| 250 pps | 4 ms | 78.75°/秒 |
| 500 pps | 2 ms | 157.5°/秒 |
| 1000 pps | 1 ms | 315°/秒 |

例如 600 pps 对应 1 ms，实际为 1000 pps；首版使用实际速度档位，并在到位后等待
该轨迹段剩余时间。允许 1000 pps，但不将所有动作固定为最高速度。

按最新确认固定软件边界：水平 −80°～+80°，俯仰 −20°～+10°；协议俯仰负为向上、
正为向下。当前四个动作最大水平偏转 30°，低头幅度缩小到 +10°。

动作幅度与节奏以约 90% 精度为目标，不要求步进量化后的角度逐点完全相等。
协议角度先转换为 0.1° 的整数目标；判断到位和回中采用绝对角度容差，初始为 ±0.4°，
避免以 0° 的相对百分比判定，也避免对不足半拍的目标反复补发。
回中插值始终限制在软件行程内，包括 10° 目标量化后上报为 10.1° 的情况；
反馈原值保留用于时间计算，不把超出边界的反馈角度原样作为下一条目标下发。

## 四种动作

模拟器每次先用 0.28 秒平滑回到 pan=0、tilt=+8 的基准。+8 是模拟器的上仰模型基准，
实物默认以协议归零中心 (0,0) 为基准。按方向约定进行相对转换：

```text
pan_hw  = pan_home + pan_sign * pan_sim
tilt_hw = tilt_home - 0.5 * (tilt_sim - 8)
```

首版 `pan_home=0`、`tilt_home=0`、`pan_sign=+1`，实板用参考正负角度帧确认方向。
俯仰变化按 0.5 缩放，将模拟器 SAD 的 20° 低头变为实物可达的 10°，保留缓动曲线。
模拟器的随机幅度 v 固定为 1，惊讶方向固定向右，避免初次验证引入随机结果。

| MCP 场景 | 对应 UI | EB521 轨迹 | 模拟器名义运动时间，另加基准过渡 |
| --- | --- | --- | --- |
| emotion.happy | HAPPY | 水平 ±6°，0.8 Hz 正弦摆动；俯仰0° | 2秒 |
| emotion.sad | SAD | 水平0°，俯仰0°→+10°，缓慢低头 | 3秒 |
| emotion.angry | ANNOYED | 水平0°→+8°→−8°→+10°；俯仰0° | 1.2秒 |
| emotion.surprised | SURPRISED | 水平0°→+30°→+25°；俯仰0° | 0.8秒 |

模拟器没有 ANGRY；用现有 ANNOYED 的“不满”图案和机械关键帧承接 angry。
四个动作均追加平滑回中段，并等待回中完成。模拟器原始末姿分别为 sad 低头、angry
+10°、surprised +25°，happy 的2秒曲线末尾约−3.5°；设备端按用户要求回中，
因此总时长包含基准过渡、表中动作时间和回中收尾。收尾初始按 0.28 秒规划；
若实际串行执行超过名义时间，则等待完成，不积压轨迹点。

平滑采用模拟器的五次缓动 `6u^5 - 15u^4 + 10u^3`，用有限关键点/查表发送，
不会直接将浏览器逐帧角度连续塞进 UART。按有限小段保留幅度、方向和顺序；
每段选择能在名义时间内到达目标的实际速度档位，完成确认后补齐剩余时间，
再推进下一段；如有新动作或挂断请求，则跳过旧段剩余等待，转入新动作或回中。
不足半拍的段合并或仅等待，持续使用绝对目标避免微小相对位移被全部丢弃；
关键转折点必须保留。
happy 的峰值约 30.2°/秒，可用 100 pps；缩幅后的 sad 峰值约 6.25°/秒，可用 20 pps；
surprised 的快速转头峰值约 148°/秒，
可用 500 pps；angry 的快速摆头峰值约 178°/秒，需要允许 1000 pps。
协议处理及通信时间纳入实际节奏；段结束后不追赶补发过时轨迹点。

## 场景调度与生命周期

平台 `lcd_sdk_render()` 在最新状态合并之前提取一次性表情位，复制一个动作枚举及请求序号。
普通 VP/服务端状态刷新不能覆盖或重播该请求。保持一个正在执行动作和一个最新待执行请求；
新请求仅覆盖未下发的旧轨迹，当前已下发的小段必须先确认完成；随后从当前位置
进入新动作的基准过渡，不通过 `0x64` 抢停。同一表情也按新请求重新触发。
SDK 已处理相同 command ID 的去重，平台不再根据表情枚举作去重。

云台 owner 负责 UART、应答、运动阶段和超时。只用一个新增的有限等待工作线程，
优先级低于音频任务，初始栈预算4 KiB，再以目标栈高水位验证；协议缓冲、请求槽和动作表固定。
UI 仍由原显示 owner 操作，场景将四个已有表情和请求序号投递给它，支持同名表情重播；
不在 UART worker 直接调用 LVGL，不在 SDK render/RTM 回调阻塞等待机械动作。
锁只用于复制/取出请求，释放请求锁后才调用显示接口，避免与 LCD snapshot 锁形成反向依赖。
跨任务字段使用既有 RTOS 互斥锁或 AOSL 原子接口，不新增 GCC 通用原子操作。
云台 worker 单独持有一份 AOSL 引用，关闭失败保留该引用；退出并完成资源清理后才释放，
避免产品先关闭时仍运行的 worker 访问已退出的日志运行时。RX 由轻量 ISR 通知，不周期性
空读 UART，通知对象保留至进程结束以避免跨核 ISR/退出通知访问已释放 semaphore。

初始化接入 `mybot_bk7259_platform_prepare()`，关闭接入完整 platform shutdown。
SDK detach、退出会话/断网、进入配网或恢复出厂均使未下发的旧轨迹失效；
工作请求带平台自己的取消序号，防止旧完成事件再触发 UI 或后续轨迹。
当前段的应答及完成确认仍由云台 owner 负责。SDK 生命周期仍由 SDK 维护，平台序号只表示
异步工作有效性，不撤销已经发给控制器的命令。

正常挂断优先取消未下发轨迹；当前小段结束后，在已归零、通信正常时执行回中，
并等待回中完成。挂断回中请求优先于普通表情请求；退出会话后的迟到表情不重新启动动作。
进入配网或恢复出厂同样取消轨迹并回中；完整关闭使用有限等待收完当前段及回中，
不能用 `0x64` 假定清空旧任务。UI 状态更新和 RTC 退出无需同步等待机械回中；
恢复出厂的最终重启需留出有界的回中完成时间。普通状态指示保持第三行原有状态/VP。
通信或执行失败不停止现有语音会话；标记云台故障、停止继续下发、记录正式日志。
完整关闭等待 worker 退出后才释放 UART/GPIO，退出失败保留仍被使用的资源。
